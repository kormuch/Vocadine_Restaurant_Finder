Das Problem — Wer ist Sarah?

Die Nutzerin

  • 28 Jahre alt, Englisch-Muttersprachlerin
  • Kommt in eine unbekannte deutsche Kleinstadt
  • Kein Lokalwissen, kein Deutsch
  • Möchte eine Restaurantempfehlung — ohne zu tippen

Das Szenario

Sarah öffnet VocaDine, spricht frei auf Englisch. Das System stellt gezielte Fragen, sucht passende Restaurants und liest die Empfehlungen vor. Kein Bildschirm nötig.

Warum kein Tippen?

  • Hände belegt (Koffer, Kind, Karte)
  • Tastaturlayout unbekannt
  • Sprachassistenz ist natürlicher für spontane Entscheidungen

Der Scope

  • Englische Eingabe, deutsche Städte
  • 10-Slot-Dialog
  • 3 Restaurantempfehlungen + Vorlesung

Designprinzip

Vollständig deterministisch. Kein LLM-Call für NLU. Keine Halluzinationen. Geschlossene Domäne: 10 definierte Slots, endliches Vokabular.

Kein Framework

Kein Flask, kein Rasa, kein FastAPI. Gesamte Runtime-Logik in einer main.py. Übersichtlich, nachvollziehbar, prüfbar.

2b. NLU — Regelbasierter Fallback

Was der Fallback abdeckt

  • 5 weitere Slots: occasion, datetime, distance, special_features, past_experience
  • 20+ Cuisine-Typen als Keyword-Map
  • 20+ Budget-Phrasen (cheap, expensive, …)
  • 10+ Occasions (birthday, date night, …)
  • Regex für Gruppengröße ("table for 4")

Besondere Features

Schlüsselstrategien

Implizites Slot-Filling
Offene Eingangsfrage: User kann 2–3 Slots in einem Satz füllen. Weniger Turns, natürlicherer Dialog.

Probe-Validation
Bei location/cuisine: Google Places API vorab anfragen. 0 Ergebnisse → Slot zurücksetzen + nachfragen.

Impatience Detection
VADER-Sentiment < −0.5 oder Stop-Keywords ("just search") → alle offenen Slots mit "any" füllen, Suche startet sofort.

4. Recommendation Engine — TF-IDF + Rating

Score-Formel

score = (cosine_sim × 0.4)
+ (google_rating / 5.0 × 0.6)
+ Boni

Warum 40/60 Gewichtung?

  • Touristen haben kein Lokalwissen
  • Google-Rating = Tausende aggregierte Bewertungen → stabiler Qualitätssignal
  • TF-IDF-Confidence degradiert bei kurzen Venue-Typ-Strings

TF-IDF — Warum nicht BERT?

TF-IDF wird on-demand auf API-Rückgaben berechnet (nicht offline trainiert). Domänen-spezifische Begriffe (Cuisine-Typen, Diäten) werden von allgemeinen Embeddings schlecht abgebildet.

TF-IDF ist transparent, deterministisch, matched exakt auf Venue-Daten.

Keine LLM-Abhängigkeit

  • Keine Token-Kosten
  • Keine Rate Limits
  • Keine Halluzinationen
  • Kein API-Key für NLU

Warum diese Architektur? — Häufige Fragen

„Warum kein ChatGPT / LLM?"

Closed-Domain Slot Filling braucht kein Sprachmodell. 10 Slots, endliches Vokabular. Determinismus > Kreativität. Keine Halluzinationen, keine Token-Kosten.

„Warum spaCy statt BERT?"

600 Utterances sind zu wenig für Transformer-Fine-Tuning. spaCy's CNN-NER ist für kleine Domänen effizient und schnell (Millisekunden).

„Warum TF-IDF statt Sentence Embeddings?"

Domänen-spezifische Begriffe (Cuisine-Typen) werden von allgemeinen Embeddings schlecht abgebildet. TF-IDF ist transparent und matched exakt auf Venue-Daten.

„Macro-F1 = 0.881 — reicht das?"

Für 600 Trainingsbeispiele in einer Closed-Domain: ja. Schwache Labels (GROUP_SIZE, BUDGET) werden vom Rule-System aufgefangen. Das Gesamtsystem ist robuster als der NER-Score allein zeigt.

„Vibecoding — wo ist die Eigenleistung?"

Architekturentscheidungen (deterministisch vs. LLM, TF-IDF vs. Embeddings, Probe-Validation, Impatience Detection, phonetische Whitelist) sind konzeptionelle Designentscheidungen. Jede ist begründet und dokumentiert.
