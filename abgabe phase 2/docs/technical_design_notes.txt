PURPOSE
This document provides technical justifications for design decisions
that go beyond the scope of the 10-slide presentation.
Intended audience: course tutor / examiner.


1. RECOMMENDATION ENGINE — PRICE SIGNAL DESIGN

Google Places API (New) returns priceRange.endPrice in EUR rather than
the legacy price_level (integer 1–4). This is a more precise signal:
  - cheap:      endPrice <= 15 EUR
  - moderate:   16–35 EUR
  - fine dining: > 35 EUR

Design decision: priceRange is used as a +0.1 bonus signal (budget_bonus),
not as a TF-IDF feature. Rationale: price is a hard constraint — a user
who requests "cheap" should not see expensive restaurants ranked higher
simply because the word "affordable" appears in their reviews. Separating
it as a structured bonus outside the cosine similarity calculation
enforces the constraint cleanly without polluting the text-based
preference matching.

price_level was not used because it is deprecated in Places API (New)
and not reliably populated. endPrice is the recommended replacement.


2. TF-IDF WEIGHTING (40/60 cosine / rating)

The 0.4/0.6 split is a deliberate design choice, not empirically optimised.
Reasoning: on short restaurant descriptions (name + types alone),
TF-IDF cosine similarity produces low-confidence scores due to sparse
vocabulary overlap. Google's aggregate rating is a crowd-sourced quality
signal averaging hundreds of reviews — more stable and semantically
meaningful than keyword overlap on 20–50 word descriptions.

When reviews and editorialSummary are available (which they are for
most results in populated German cities), the cosine signal becomes
stronger and the 40/60 balance becomes more justified.

A 50/50 split was considered but rejected: in cases where the TF-IDF
signal degrades (generic types only), a higher rating weight ensures
the user still gets objectively well-reviewed restaurants rather than
random results.


3. NLU ARCHITECTURE — WHY LAYERED (spaCy + rules)

The trained spaCy NER model covers 5 labels: LOCATION, CUISINE, DIET,
BUDGET, GROUP_SIZE. Rule-based fallbacks remain active for:
  - Slots not covered by NER: datetime, distance, occasion, special_features
  - GROUP_SIZE implicit expressions: "me and my wife" (not an annotatable span)
  - Budget negation: "not too expensive" (span boundary detection challenging)
  - GERMAN_CITIES whitelist: 2058+ entries with phonetic aliases for STT correction

This layered approach means the trained model handles generalisation
(unseen phrasings, synonyms) while rules handle the closed-domain
edge cases where precision is more important than recall.


4. STT — GOOGLE WEB SPEECH API LIMITATIONS

The Google Web Speech API (en-US) was chosen for its zero-setup
integration via the SpeechRecognition library and reliable accuracy
on standard English. Known limitations:
  - Small German city names fail consistently (mitigated by phonetic alias system)
  - Short words ("no", "two") have ~20% WER — mitigated by word-boundary
    regex and context-aware slot extraction
  - Cloud dependency: audio is sent to Google servers (see Privacy section)
  - pause_threshold reduced from 2.5s to 1.8s to reduce perceived latency

Alternative considered: OpenAI Whisper (local). Rejected for prototype
due to higher setup complexity and GPU dependency for real-time use.


5. PRIVACY — DATA FLOWS

Data leaving the device:
  a) Audio: sent to Google Cloud via Web Speech API during recognizer.listen()
     Google's terms: audio processed, not stored for advertising.
     Microphone is only active during active listen() call — not always-on.

  b) Location + preferences: sent to Google Places API as a textQuery string
     e.g. "Italian vegan restaurant in Berlin"
     No persistent user profile is created by VocaDine server-side.
     Google Places API terms apply to the query data.

  c) API key: stored exclusively in .env file, excluded from repository
     via .gitignore.

For a production deployment handling tourist location and dietary data,
GDPR Article 13 transparency obligations would apply before first use.
The current prototype is scoped to a single-user research context.


6. EVALUATION — HONEST FRAMING

NER test set (90 utterances, held out before training):
  LOCATION:   F1 = 0.981
  DIET:       F1 = 0.971
  CUISINE:    F1 = 0.925
  BUDGET:     F1 = 0.818
  GROUP_SIZE: F1 = 0.711
  MACRO:      F1 = 0.881

GROUP_SIZE is the weakest label. This is an architectural boundary,
not a model failure: expressions like "me and my wife" or "me and my
family" cannot be annotated as NER spans (there is no explicit number
in the text). The rule-based layer handles these cases. The NER model
handles explicit numbers and word forms ("two", "four", "a party of six").

BUDGET F1=0.818: multi-word budget spans ("not too expensive",
"somewhere in between") are challenging for span boundary detection
in a blank model with no pre-trained vectors. The rule-based keyword
map covers the most common variants as fallback.


7. EDGE-TTS vs. pyttsx3

pyttsx3 was the original TTS choice (Phase 1 concept). During development
it produced consistent environment errors in Spyder and IPython contexts
(COM object errors on Windows, audio driver conflicts). These were not
reliably reproducible but occurred frequently enough to block testing.

edge-tts uses Microsoft Azure Neural voices via a lightweight async
Python library. Advantages: neural voice quality, no API key required,
no environment compatibility issues observed across test setups.
Disadvantage: requires internet connection (cloud TTS). For a
tourist-facing app this is acceptable — the user is online by assumption.
